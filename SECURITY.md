# Security policy

polyjose is a cryptographic library, so we treat security reports as top priority.

- **Report privately** through GitHub Security Advisories ("Report a vulnerability" on the repo's Security tab). Don't open public issues for vulnerabilities.
- We acknowledge reports within 72 hours and aim to publish a fix and an advisory within 30 days.
- **In scope:** signature or MAC bypass, algorithm confusion, key or plaintext disclosure, timing side channels in polyjose's own code, panics on untrusted input, and binding-level memory issues.
- **RSA private-key operations (RSA signing and RSA-OAEP-256 decryption):** RSA comes from the RustCrypto `rsa` crate, the only pure-Rust implementation. polyjose uses `rsa` 0.10.0, the first release that [RUSTSEC-2023-0071](https://rustsec.org/advisories/RUSTSEC-2023-0071) (the Marvin timing side channel in private-key operations) lists as patched, and `cargo deny` checks it with no ignore. polyjose signs (`RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`) and decrypts (`RSA-OAEP-256`) only through `rsa`'s blinded entry points, with randomness from the OS CSPRNG, and a build check rejects any other private-key path. RSA-OAEP-256 decryption never reports why an Encrypted Key failed: it substitutes a random content key, so the failure looks like any other `DecryptionFailed` (RFC 7516 §11.5). The evidence for constant-time behaviour is upstream's verification of its constant-time code with BINSEC (`cargo checkct`), and polyjose's own dudect-style statistical timing test (valid against invalid OAEP ciphertexts, and signing different messages, with a positive control that must detect a known public-input difference). The signing test is evidence about message dependence only: both of its classes use the same key, so it says nothing about dependence on the private key, which rests on `rsa`'s blinding. There is no Marvin-toolkit run, and the `rsa` 0.10 rewrite has no published independent audit. Two known deviations of `rsa` 0.10.0: RSA-OAEP decryption does not check that the first octet of the encoded message is zero (RFC 8017 §7.1.2 step 3.g), which cannot help an attacker in JWE (anyone with the public key can already encrypt any content key, and the content key is authenticated by the tag); and private keys whose two primes differ in size by more than the half-modulus width are refused on import (`InvalidKey`). RSA key generation, multi-prime keys and `RSA1_5` (in either direction; RFC 8725 discourages it) are not implemented, and no feature flag turns them on.
- **Residual risk: RSA private-key zeroization inside `rsa` 0.10.0.** polyjose wipes its own copies of RSA private members, and `rsa`'s private key wipes itself on drop. But `rsa`'s big integers (`BoxedUint`) are `Zeroize`, not `ZeroizeOnDrop`: on the error paths of `PrivateKey::from_components` (a key that fails validation) and in some of its intermediate values, secret limbs may be freed without being wiped. Keys from import are validated once, so this touches only rejected keys and transient values inside `rsa`; a fix belongs upstream.
- **Residual risk: UniFFI copies of secret outputs (Kotlin, Swift).** UniFFI 0.32.2 writes a returned record into a buffer that the host frees unwiped, and polyjose can't reach those copies without `unsafe` (ADR 0058). `JwsVerified.payload` leaves at least 2 full Rust-heap copies; `JwsUnverified.payload`, from `decodeJwsUnverified`, leaves the same; so do `JweDecrypted.plaintext` and `JweDecrypted.aad`, and a private-key string result leaves 1. Wipe the `ByteArray`/`Data` you receive.
- **Unverified decode:** `decode_protected_header_unverified`, `decode_jws_unverified` and `decode_jwt_unverified` (`decodeProtectedHeaderUnverified`, `decodeJwsUnverified`, `decodeJwtUnverified` in the bindings) read a compact token's header, payload or claims without checking the signature. The rule is that nothing unverified looks verified: their names say `unverified`, they return their own types (`UnverifiedJws`, `UnverifiedJwt`; `JwsUnverified`, `JwtUnverified`), which have no top-level `alg` and no conversion to a verified result, and they take no key and run no claim validation. They run the same parsing, limits and error codes as verification up to the signature, and accept `none`, an unknown `alg` or an unknown `crit` entry only as data; verification still refuses all three. A JWE payload can't be read without its key. A way to pass an unverified result off as verified is in scope.
- **No SHA-1.** polyjose does not implement `RSA-OAEP` (SHA-1); use `RSA-OAEP-256` or ECDH-ES.
