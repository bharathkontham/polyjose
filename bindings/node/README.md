# @polyjose/node

polyjose for Node.js: JOSE (JWS, JWE, JWK and JWT; RFC 7515 to 7519) implemented in pure Rust and
loaded as a Node-API addon. All cryptography comes from the RustCrypto and dalek crates, with no
OpenSSL. Verify and decrypt always take an explicit algorithm allow-list, and `none` is never
accepted (RFC 8725).

> Status: **pre-alpha**. Don't use it in production yet.

## Install

```sh
npm install @polyjose/node
```

npm also installs the matching prebuilt addon, `@polyjose/node-<platform>`, for macOS (x64,
arm64), Linux glibc and musl (x64, arm64) and Windows (x64, arm64). Each is an optional
dependency at exactly this package's version, and npm installs only the one for your platform.
If you install with `--omit=optional`, no addon is installed and the import throws.

## Module format

- The package is **ESM only** and needs **Node.js 22.12 or later**.
- CommonJS code can still load it with `require("@polyjose/node")`, through Node's `require(esm)`
  (unflagged since 22.12).
- Every operation returns a Promise. The work runs on the libuv thread pool, so it doesn't block
  the event loop.
- The API and its TypeScript types are the same as `@polyjose/wasm`, so you can switch between
  the two packages by changing the import.

## Documentation

Guides and the API reference are at <https://polyjose.dev>. The Node.js guide is at
<https://polyjose.dev/start/node/>.

## Loading the addon

The loader (`binding.cjs`, generated by napi-rs) picks your platform's addon:
1. a local `polyjose.<platform>.node` next to it;
2. then the platform package `@polyjose/node-<platform>`, found through Node's normal module
   resolution: this package's `node_modules`, then every ancestor `node_modules`, then
   `NODE_PATH`.

Paths are resolved against the loader's own directory, never the working directory. On its own,
the loader returns the first module it can load, even a JavaScript file planted in one of those
places. So the package wraps it and loads **only polyjose's native addon at this package's
version**. Otherwise the import throws, and nothing it refused has run:

- **Before loading,** everything the loader could pick must be a native `.node` file. If any
  candidate resolves to something else, such as a JavaScript `@polyjose/node-<platform>` in a parent
  folder or on `NODE_PATH`, the import throws before that file runs.
- **After loading,** the result must be exactly one native addon, not wrapped by any JavaScript,
  and its own `version()` must be this package's version. An addon from another polyjose release,
  such as a mismatched `@polyjose/node-<platform>`, is refused, whatever
  `NAPI_RS_ENFORCE_VERSION_CHECK` says. The loader alone checks the platform package's
  `package.json` version only when that variable is set to something other than `0`.
- polyjose **never publishes a `wasm32-wasi` package**. The napi-rs loader still has a WASI
  fallback, tried when the native load fails: `./polyjose.wasi.cjs`, then
  `@polyjose/node-wasm32-wasi`. The package never reaches it. If the native load fails, the import
  throws "Cannot find native binding". If either WASI file or package can be found from the
  loader's directory, the import throws before anything is loaded. For WebAssembly, use
  `@polyjose/wasm`.

These checks keep the package from *choosing* a substitute. They can't protect against code that
already runs in your process, which can change anything.

### Environment variables

| Variable | Effect |
|---|---|
| `NAPI_RS_NATIVE_LIBRARY_PATH` | Loads the native library at this path instead of the bundled addon. **It replaces polyjose's cryptography and all of its verification** (see below). For testing and debugging only, never in production. |
| `NAPI_RS_FORCE_WASI` | **Refused.** If it is set, whatever the value (even `false` or empty), the import throws. |
| `NAPI_RS_WASI_FLAVOR` | **Refused**, like `NAPI_RS_FORCE_WASI`. |
| `NAPI_RS_ENFORCE_VERSION_CHECK` | Read by the loader for the platform package. The package checks the version anyway (see above). |

**`NAPI_RS_NATIVE_LIBRARY_PATH` replaces the crypto implementation.** The library at that path
does every signature check, decryption and algorithm allow-list check. A library built to accept
everything makes polyjose accept forged tokens, and nothing in the package can detect it.
- The package accepts only a native `.node` file there that reports this package's version.
  It refuses a JavaScript file before running it. It can't tell polyjose's addon from another
  native library that reports the same version.
- If loading from that path fails, the loader doesn't fall back to the bundled addon.
- A process that can set its environment can already load native code (for example through
  `NODE_OPTIONS`), so this override doesn't widen what an attacker who controls the environment
  can do.
- Still, never set it in production, and don't pass an untrusted environment to a process that
  uses polyjose, such as a container whose variables come from outside.

### A panic in the addon aborts the process

If the Rust code ever panics, Node.js **aborts the whole process** (SIGABRT). The Promise isn't
rejected, and no `catch` or `process.on("uncaughtException")` handler runs. This fails closed:
no partial result is returned, and no memory is corrupted. Today we know of no input that causes a
panic; the core forbids `panic!`, `unwrap` and `expect`. A server that must survive a panic should
run polyjose in a worker process it can restart. Turning panics into rejected Promises is planned.

### Side effects of the generated loader

- **Linux:** to tell musl from glibc, the loader first reads `/usr/bin/ldd`. If that fails, it
  calls `process.report.getReport()`, and before that it sets `process.report.excludeNetwork = true`
  for the whole process. As a last resort it runs `ldd --version` in a child process.
- **Windows x64:** an embedder that runs Node as a shared library (`node_target_type` is
  `shared_library`), or a Node whose `shlib_suffix` is `dll.a`, is sent to the `win32-x64-gnu`
  addon only. polyjose doesn't publish that addon, so those hosts can't load the package.
- **`__napiBindingTarget`:** the loaded addon has an extra property, `__napiBindingTarget`
  (`"native"`), set by the loader. The package's own API doesn't export it.
