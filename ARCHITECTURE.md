# Architecture

How the polyjose repository is put together: the layers, where each binding lives, how one call travels from an app to the core, how the code is tested, and what the guard scripts enforce. [CONTRIBUTING.md](CONTRIBUTING.md) has the toolchains and two walkthroughs (add an algorithm, add a binding operation).

## 1. What polyjose is

polyjose is one pure-Rust JOSE core (`crates/polyjose`) exposed to other languages through one shared surface (`bindings/surface`), one thin adapter per binding technology (napi-rs, wasm-bindgen, UniFFI), and one host package per language (TypeScript for Node and the web, Kotlin, Swift). Every platform runs the same conformance corpus (`conformance/vectors`), and a parity check compares their results with the core's. All JOSE logic, validation, defaults and cryptography live in the core; the layers above it only convert types.

## 2. The layers

| Layer | Folders | Contains | Must not contain |
|---|---|---|---|
| 1. Core | `crates/polyjose` | JOSE, crypto composition, the strict JSON parser, every default and limit | any binding concern |
| 2. Surface | `bindings/surface` (crate `polyjose-surface`, not published) | every operation, record and result once, in plain Rust; JSON in and out through the core's parser; zeroizing of inputs; the one error type, built only from a core error | an FFI framework, serde, defaults of its own |
| 3. Adapters | `bindings/node` (napi-rs), `bindings/wasm` (wasm-bindgen), `bindings/uniffi` (UniFFI, crate `polyjose-ffi`, shared by Kotlin and Swift) | one exported function per surface operation, framework records with conversions, error conversion, zeroizing of outputs | JSON parsing, policy, defaults, crypto, any logic beyond type conversion |
| 4. Host packages | `bindings/ts-common` (TypeScript shared by `@polyjose/node` and `@polyjose/wasm`), the package entries in `bindings/node/src/*.ts` and `bindings/wasm/js/`, `bindings/kotlin`, `bindings/swift` | idiom only: Promises, object to JSON, JS type checks, the JS clock for JWT `now`, a few hand-written Kotlin and Swift members (platform keys, redaction) | policy, defaults, JOSE validation |

**The adapter rule:** an adapter function is one type conversion and one surface call. Anything more is a review finding.

The surface depends on `polyjose` and `zeroize` only. Each adapter adds only its framework crates (and `getrandom` for WASM). No layer uses serde. `bindings/uniffi-bindgen` is the pinned UniFFI generator CLI, a separate crate so that its dependencies never enter a shipped library.

```
crates/polyjose ─────────────── 1. core
       │
bindings/surface ────────────── 2. surface
       │
       ├── bindings/node ─────┐
       ├── bindings/wasm ─────┤ 3. adapters
       └── bindings/uniffi ───┤    (bindings/uniffi-bindgen generates Kotlin and Swift from it)
                              │
 bindings/ts-common ──────────┤ 4. host packages
   (+ node/src/*.ts,          │    @polyjose/node, @polyjose/wasm
      wasm/js/)               │
 bindings/kotlin ─────────────┤    dev.polyjose:polyjose (AAR), dev.polyjose:polyjose-jvm (jar)
 bindings/swift + Package.swift    Swift package Polyjose
```

Everything that exposes the core to another language is under `bindings/`, one folder per package or adapter. Repo-wide contracts stay at the top: `conformance/`, `interop/`, `fuzz/`, `scripts/`. `Package.swift` is at the root because Swift Package Manager resolves a package at the repository root.

## 3. Where is the X binding

| Platform | Folders | Gradle project | `test-all.sh` key | Workflow |
|---|---|---|---|---|
| Rust | `crates/polyjose` | — | `rust` | `ci.yml` |
| Node.js | `bindings/node` + `bindings/ts-common` | — | `node` | `binding-node.yml` |
| Web (WASM) | `bindings/wasm` + `bindings/ts-common` | — | `wasm` | `binding-wasm.yml` |
| Android (Kotlin, and Java through the AAR) | `bindings/kotlin/android` + `bindings/kotlin/shared` + `bindings/uniffi` | `:polyjose` | `android` | `binding-android.yml` |
| Java and Kotlin on the JVM (desktop, server) | `bindings/kotlin/jvm` + `bindings/kotlin/shared` + `bindings/uniffi` | `:polyjose-jvm` | `android` | `binding-android.yml` |
| Swift (iOS, iPadOS, macOS, watchOS) | root `Package.swift` + `bindings/swift` + `bindings/uniffi` | — | `swift` | `binding-apple.yml` |

The names differ in three places, on purpose: the folders are named by language, while the test-all keys and workflow names are older and scripted. `bindings/kotlin` is test-all `android` and `binding-android.yml`, and builds both the AAR and the JVM jar. `bindings/swift` is test-all `swift` and `binding-apple.yml`.

**Java:** the Kotlin API is generated by UniFFI. Java code can call it, but awkwardly: members that take Kotlin `UInt` get mangled names, and Kotlin default arguments don't exist in Java. See [Not supported → Java](https://polyjose.dev/security/not-supported/#java).

## 4. One call, end to end

`jwsVerifyCompact` from a Swift app:

1. The app calls `jwsVerifyCompact(token:key:options:)`, declared in `bindings/swift/Sources/Polyjose/Polyjose.swift` (generated by UniFFI, committed). It lowers the arguments and calls a C symbol of `libpolyjose_ffi`, inside `PolyjoseFFI.xcframework` (built by `bindings/swift/scripts/build-xcframework.sh`).
2. The adapter `jws_verify_compact` in `bindings/uniffi/src/jws.rs` puts the key into a zeroizing owner, converts the options record, and makes one call.
3. The surface `jws_verify_compact` in `bindings/surface/src/jws.rs` parses the JWK with the core, builds the core's verify options from the allow-list, and calls the core.
4. The core `polyjose::jws::verify_compact` in `crates/polyjose/src/jws/compact.rs` does the work (RFC 7515 §5.2, RFC 8725 §3.1). Its result or error travels back up the same path; the error code is the core's.

Kotlin takes the same path: the generated Kotlin (built from the same library at build time) calls `libpolyjose_ffi` through JNA, and steps 2 to 4 are identical.

The same call from JavaScript:

1. The app calls `jwsVerifyCompact(token, key, options)` from `@polyjose/node` (entry `bindings/node/src/index.ts`) or `@polyjose/wasm` (entry `bindings/wasm/js/index.ts`). Both export the facade that `createApi(backend)` in `bindings/ts-common/src/api.ts` builds: it type-checks the arguments, serializes the JWK object to JSON, and returns a Promise.
2. The facade calls the package's backend, whose contract is `bindings/ts-common/src/backend.ts` ([BACKEND.md](bindings/ts-common/BACKEND.md)). For Node, `bindings/node/src/backend.ts` loads the hash-checked native addon; for WASM, `bindings/wasm/js/backend.ts` wraps the wasm-bindgen glue.
3. The adapter `jws_verify_compact` in `bindings/node/src/jws.rs` (napi-rs; it runs on the libuv thread pool) or `bindings/wasm/src/jws.rs` (wasm-bindgen) converts the arguments and makes one surface call.
4. Steps 3 and 4 of the Swift path follow unchanged.

## 5. Data across the boundary

- **JSON values** (JWKs, JWK Sets, headers, JWS and JWE JSON serializations): Kotlin and Swift pass `String`s. JS takes a string or a plain object and returns plain objects for JWKs and headers. Every JSON text is parsed by the core's strict I-JSON parser, so duplicate members and the depth and size limits behave the same everywhere.
- **Tokens** are strings everywhere. **Bytes** are `Uint8Array`, `ByteArray`, `Data` and `&[u8]`.
- **Allow-lists are required.** Every verify and decrypt record has `allowedAlgs` (and decrypt has `allowedEnc`) with no default. In Kotlin and Swift omitting one does not compile; in JS a missing list arrives as an empty list, which the core rejects with `AlgorithmNotAllowed`, as it rejects a `none`-only list (RFC 8725 §3.1).
- **Defaults live only in the core.** Every tunable is optional, and an absent value means the core's default.
- **Error codes are the contract.** Every failure carries a stable code string from the core's `Error::CODES` (JS `PolyjoseError.code`, Kotlin `PolyjoseException`, Swift `PolyjoseError`, each with `code()`). No error message contains input or key material; a marker test on every platform checks this.
- **Algorithm names are strings** in every binding, so a new algorithm in an existing family needs no binding change.

## 6. Tests

Every package has a `test.sh`, and `scripts/test-all.sh <keys>` runs them (keys `rust`, `wasm`, `node`, `android`, `swift`, plus `tooling`). The table below maps each kind of test to its wrapper and to the native command behind it, for running one suite or one test from an IDE or a tool.

- **"Wrapper"** is the supported entry point: the package's `test.sh` or a `test-all.sh` key. It builds, generates and tests in the right order, and it writes the conformance results file that parity reads. polyjose has no CI on pull requests, so these local runs are the gate.
- **"Native command"** is what the wrapper ends up invoking. `<kotlin>` = `bindings/kotlin`.
- **"Needs first"** lists what must exist on a fresh checkout. **Not standalone** marks a row where the native command alone does not reproduce the wrapper's run.
- **"Runner"** is the name in `target/conformance/<runner>.json`. `test-all.sh` lists the runners per platform in `results_runners`.

**Results files and parity.** Each conformance runner writes one results document, `target/conformance/<runner>.json`: the outcome of every vector and the `vectors_digest`, a hash of the vector files' bytes. `scripts/conformance-parity.sh` compares every runner's document with `rust-core.json`. A binding cannot pass by running fewer vectors, skipping one for another reason, or failing with a different error code, and a runner that read other vector bytes fails on the digest. The format, the skip rule and the operation mapping are in [conformance/README.md](conformance/README.md).

**Two kinds of test data.** `crates/polyjose/tests/third_party` holds raw upstream corpora (JSONTestSuite, Wycheproof, the RFC 7520 cookbook JSON) that only the Rust tests read, each with its license. `conformance/vectors` holds polyjose's own cross-platform vectors, digested and run by every binding; RFC 7520 appears there too, converted to the vector format. Moving the raw corpora into `conformance/vectors` would make every platform load them and change the digest, so they stay apart. `cfg(test)` modules inside `crates/polyjose/src` (for example `keys/oracle_tests.rs`) are unit tests that need crate-private access; their place in `src/` is deliberate.

## 7. Guards

Each guard runs in every `test-all.sh rust` run; their own self-tests are `test-all.sh tooling`.

- `scripts/check-deps.sh`: the core's dependency tree is exactly `deps-allowlist.txt`, and each binding crate's is `bindings/deps-allowlist/<name>.txt` (file name = folder under `bindings/`); crates.io only, no patches, no build script in the core, and the credits in `CREDITS.md` match.
- `scripts/check-binding-api.sh`: each binding's exported names (operations, records, fields, error codes) equal `bindings/api-inventory.txt`, one mode per binding in `scripts/check-binding-api.d/`.
- `scripts/check-rsa-symbols.sh`: on compiled output, RSA private-key operations go only through the `rsa` crate's blinded entry points; no key generation, `RSA1_5` or unblinded path.
- `scripts/check-test-vectors-off.sh`: nothing that builds a binding can enable the core's `insecure-test-vectors` feature (a deterministic RNG for reproducing published vectors).
- `scripts/check-no-cargo-config.sh`: no cargo configuration file in the repository, and none set by a script or workflow, so no source replacement, rustflags or wrapper can sneak in.
- `cargo deny --all-features check` ([deny.toml](deny.toml)): no C or assembly crypto crate (OpenSSL, `ring`, `aws-lc`), allowed licenses only, crates.io as the only source.

## 8. Generated code

- `bindings/swift/Sources/Polyjose/Polyjose.swift`: UniFFI output, **committed**, because Swift Package Manager cannot run the bindgen. `bindings/swift/scripts/check-generated.sh` regenerates it and fails on any difference. `.gitattributes` marks it `linguist-generated`, so GitHub collapses it in diffs.
- The Kotlin API: generated at build time by the `uniffiGenerate` task into `bindings/kotlin/build/generated/uniffi/kotlin` (and patched there by `build-logic`'s `UniffiKotlinPatch`). Nothing generated is committed.
- `bindings/ts-common/src/error-codes.ts`: the `ErrorCode` union, generated by `npm run build` from the core's `Error::CODES`; git-ignored.
- `bindings/wasm/tests/vectors/mod.rs`: the embedded vector index for the wasm test runner, generated and committed (see the WASM vector index row).

## 9. Design records

Code comments cite design records as `ADR NNNN §n`. These are the maintainers' internal records and are not published. This document and the READMEs summarise what a contributor needs from them; if a comment's reasoning is unclear, ask in an issue.
